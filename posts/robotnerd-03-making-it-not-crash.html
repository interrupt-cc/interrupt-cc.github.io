0x5: Making It Not Crash

DATE: 2026-07-14 | PROJECT: ROBOTNERD

Here's a truth about building software fast with an AI agent: you ship bugs faster too. The app worked. It also crashed, stuttered, and occasionally got stuck. That's not a crisis — it's just the bill that comes with building rich UI quickly. You pay it and move on.

July 14th was reliability day. But I want to reframe what "reliability day" actually meant here, because the story isn't "oh no, it kept crashing." The story is that I had a system where crashes didn't slow me down, because the Telegram bot was always there as a fallback, and because the app could report its own failures. That combination is what made rapid iteration possible.

This devlog is a quick tour of the crashes — and then the part that actually matters: the self-debugging loop.

The Usual Compose Suspects

If you build a Jetpack Compose app that streams, animates, and renders rich content, you hit a predictable set of walls. Here are the ones I hit:

The scroll crash. Rendering messages with an AndroidView wrapping a WebView — powerful but heavy. Scroll fast through a long history and you're tearing down native views faster than the platform can keep up. Fix: rip out the AndroidView entirely, render in pure Compose. Scrolls like butter now.

Streaming stutter. Each token recomposed the entire message list. Fix: Compose stability annotations, stable list keys, and delta batching — flush tokens to the UI on a frame-aligned cadence instead of token-by-token. Same principle for the particle system: animate on the frame clock.

"Stuck on Connecting." The connection state machine treated "caught up and idle" as "still connecting." Fix: distinguish "waiting for the first event" from "waiting for the next one."

Layout crashes, keyboard eating the top bar, broken text selection, particles dying instantly. Each was its own small commit — a line or two. The kind of fiddly thing that takes an afternoon to find and a minute to fix. None of them are clever. They're just the work.

The Real Story: The Telegram Fallback

Here's what made all of this manageable: the crashes didn't stop me.

When the app crashed, I didn't reach for a USB cable and logcat. I switched to Telegram — where the original bot was still running, solid as ever — and told the agent what happened. The bot would investigate, fix the code, build a new APK, publish it to the APK server, and I'd install it over Tailscale and try again. The whole loop took minutes.

That's the value of never decommissioning your fallback. The new app was the future, but the old bot was the tool that built the future. I always had a working path to my agent, no matter what state the app was in.

The Self-Debugging Loop

And then there's the piece that made it even better: the app reports its own crashes to the agent.

The pipeline:

  1. The app installs a global uncaught-exception handler.
  2. On crash, it captures the full stack trace and POSTs it to the server's /crash endpoint.
  3. The server persists the crash report to disk.
  4. I tell the agent "the app crashed" and it reads its own crash reports.
  5. The agent reads the stack trace, identifies the bug, and fixes it.

The app tells the agent how it died, and the agent brings it back. Over the network, from my phone in my pocket. No debug cable, no logcat window, no reproduction steps to type out. The crash report is the reproduction step.

There was even a bug in the crash reporter itself — a local path variable shadowed the path module, so crashes weren't being persisted. The agent found and fixed that too. The immune system had a bug in its immune system, and it healed itself anyway.

Commits: "feat: POST /crash endpoint", "feat: /crashes command + GET /crash", "fix: crash reports not persisted — local 'path' var shadowed path module"

Why This Is The Point

This is the loop that makes the whole workflow viable, and it's worth stating plainly:

Crashes are inevitable. What matters is the recovery time.

With the Telegram bot as a fallback and the crash reporter closing the loop, my recovery time was minutes. Crash → switch to Telegram → agent reads the trace → agent fixes it → agent publishes a new build → install → done. The app never had to be perfect, because the system around it was resilient.

That's the real lesson of reliability day. It's not "write fewer bugs" — it's "build a system where bugs are cheap to fix." Keep your fallback running. Give your app a voice to report its own failures. Make the fix-loop fast. Then crashes are just part of the rhythm of building, not a crisis.

By the end of July 14th, the app streamed smoothly, scrolled without dying, connected reliably, and reported its own failures. It was solid enough to stop worrying about whether it worked — and start thinking about what it should feel like. Which is when the modem showed up.
