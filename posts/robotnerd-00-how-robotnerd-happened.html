0x3: How RobotNerd Happened

DATE: 2026-07-19 | PROJECT: ROBOTNERD

I wanted a coding companion that lived on my phone.

Not a terminal REPL with an autocomplete. Not a browser tab I'd forget was open. Something I could pull out of my pocket, say "add an OAuth login flow," and have a real autonomous agent actually do it — read the files, write the code, run the build, and show me what changed — all over my own network, while I watched particles dance and a modem sang.

I built it in nine days. This is how it happened.

The Premise

The shape of the thing was always clear:

  • A shared agent living on my home server — the kind that calls tools, reads and writes files, runs shell commands, and drives itself in a loop.
  • A phone app as the interface — chat, streaming responses, inline approvals for edits, push notifications.
  • My own network in between — Tailscale, because the agent needs to reach the codebase and the phone needs to reach the agent, and I'm not opening ports or depending on anyone's cloud.

The agent was the brain. The phone was the body. The goal was to make talking to a codebase feel like talking to a person.

The Strange Part

Here's the bit that makes this worth a devlog instead of a project page:

I built the whole thing by pair-programming with the kind of agent it became.

Day one, it was a Telegram bot with an OpenAI SDK and a handful of file tools. I'd message it: "refactor the state into a module." It would. Then I'd say "now make yourself a real app," and it did. By the end I was directing the work through the app I'd just built it to become — opening a session called "multi-project: server + app updates" and telling the agent to finish its own UI.

It's self-referential in the way that's either elegant or slightly unsettling, depending on the hour.

The Stone Knife

One decision I'd make again every time: I never shut down the original Telegram bot.

The bot was crude — a webhook, no UI, no streaming, 4K message limits. But it was solid. It had loop detection and self-healing recovery. It had been battle-tested over two days of real work. So when I started building the shiny new Android app, I left the bot running.

This turned out to matter enormously. The new app was the future, but it was new — it crashed, it stuttered, it needed iteration. And every time it did, I'd switch to Telegram, tell the bot what happened, and it would fix the app. Then I'd install the new build and keep going. The bot was my stone knife: the reliable tool I reached for while building the laser.

Even now, as I write this, the Telegram bot is still running — alongside the new HTTP+SSE server, and the app. They're not rivals. They're the same brain with two mouths. Having that second mouth around while building the first was the most practical redundancy I could ask for.

The Big Win: A Local-First Software Hot Rod

Here's what I was really building toward, and what excites me most: a coding workflow that's local-first, modular, and self-enabling.

The agent talks to any OpenAI-compatible endpoint. Point it at a cloud API, or at an Ollama instance running on another machine on your tailnet, or at DeepSeek, Cerebras, GLM — whatever you want, whenever you want. The whole thing can run fully local, fully offline, on your own hardware. Or you swap in a cloud model for the hard reasoning and swap back. It's modular by design — a software hot rod where every part is swappable.

But here's the part that makes it more than an app with a settings menu: it enables its own upgrade. The app doesn't just have options — it gives you the power to create new options, by writing software. You think of a feature, you tell the agent, it writes the code, it builds the APK, it publishes it to the APK server over Tailscale, and you install it on your phone — all in one loop, all on your own network, in minutes. The tool builds the tool.

That's the workflow I wanted: a creative engine that stays as local as you want it, that you can reconfigure without asking anyone's permission, and that gets better every time you use it because you're the one making it better.

The Arc

The build fell into five phases:

1. The brain (Jul 10–11). Start in Telegram — zero UI, instant transport, all focus on making an agent that doesn't destroy itself. The OpenAI function-calling loop, a token-efficient apply_patch tool, and the two guardrails that keep autonomous agents alive: structural loop detection and self-healing recovery. → Read the devlog

2. The body (Jul 12–13). Telegram is a fine incubator but a terrible home. So: a Jetpack Compose Android app, a new HTTP+SSE server, inline edit approvals, and — the thing that made the whole workflow real — an APK server over Tailscale that let the agent ship builds directly to my phone. The transport layer swaps; the brain stays; the bot stays. → Read the devlog

3. Making it survive (Jul 14). New apps crash. That's fine — I had the bot to fall back on, and the real achievement wasn't avoiding crashes, it was building a system where the app reports its own crashes and the agent fixes them. → Read the devlog

4. Making it sing (Jul 14–15). A coding companion shouldn't go ding. It should sound alive. So: a generative audio engine — real FSK modem synthesis on Bell 103 carriers, dub-techno ninth-chord drones through dotted-eighth feedback delay and Schroeder reverb, the agent's actual response bytes modulated into modem chirps. No audio files. Everything computed at 44.1 kHz. → Read the devlog

5. Growing up (Jul 18–19). One project became many. Sessions got titles, summaries, and a real history. The architecture evolved into a multi-project system — and taught a lesson about keeping your fallback around, because the original bot had been quietly holding sessions the whole time. → Read the devlog

The Hello World of Vibe Coding

Here's a thought I keep coming back to, and it's bigger than this project.

Every programming era has its "hello world" — the first thing you learn. Print a string. Make a webpage. Wire up a REST API. They're trivial programs, but they teach the shape of the medium.

What's the hello world of the vibe-coding era — the age where you build software by talking to an agent that writes the code for you?

I think it might be this: build your tools to build your tools.

Your first project isn't a todo app. It's your own coding companion. Not because that's the easiest thing to build — it isn't — but because once you have it, every other project becomes dramatically faster. You're not learning a language anymore; you're learning to steer a system that does the typing. And the best way to learn that is to build the steering wheel yourself.

This workflow — local models, your own network, an agent that writes and ships its own upgrades — it's a software hot rod. It's for people who want to keep their hands on the engine. And I think it's surprisingly teachable. The question isn't whether creative, seasoned engineers can do this — they can. The question is how we teach it. What's the curriculum? What's the first lesson?

Maybe the first lesson is: don't write hello world. Build the thing that writes hello world for you.

What's Next

The PROJECT_PLAN.md — written mid-build as a living blueprint — lays out the road ahead: project summaries injected into context so the agent never starts blind, a file browser for reviewing diffs on your own terms, session intelligence that titles and summarizes itself.

But the foundation is done. You open the app, you see your projects, you see the history of everything the agent ever did for each one. You tap one and pick up where you left off. Or you start fresh and the agent gets to work.

It sounds like a modem and it edits your code from across the network, and it runs on hardware I own. I'm pretty happy with it.
