0x6: Leaving Telegram

DATE: 2026-07-13 | PROJECT: ROBOTNERD

The agent could code. That was settled. But Telegram was a chat box, and what I wanted was a workshop.

Telegram gave us a chat box and took everything else. No streaming — you'd wait for a wall of text. A 4096-character limit that code doesn't fit in. No diffs, no approvals, no presence. It was the right place to start and the wrong place to stay.

But here's the thing I want to be clear about: I didn't actually leave Telegram. I built a second front end. The bot kept running — rock solid, battle- tested, always there — while I built the app alongside it. That redundancy turned out to be one of the best decisions in the project. More on that in a bit.

The Architectural Decision That Made Everything Possible

The transport is a layer, not the product.

The agent — the loop, the tools, the guardrails — didn't know or care that it was being driven by Telegram. It received messages, it produced messages and tool calls. Telegram was just the wire.

So I didn't rewrite the agent. I wrote a new server that spoke HTTP + Server-Sent Events instead of the Telegram bot API, and I plugged the exact same agent into it. The same tools. The same loop detection, the same self-healing. New mouth, same brain.

┌──────────┐   HTTP + SSE    ┌───────────────┐
│  Phone   │ ←─────────────→ │   Server      │
│  (App)   │                 │  (agent.js)   │
└──────────┘                 └───────────────┘

And critically — the Telegram bot kept running too. Two transports, one brain. When the app broke, I'd switch to Telegram. When the app worked, I'd use the app. I never had a moment where I couldn't reach my own agent.

The App: Jetpack Compose

The phone app is Kotlin + Jetpack Compose, organized as MVVM:

data/        BotClient (HTTP+SSE), repositories
model/       data classes (Session, Message, Activity)
viewmodel/   ChatViewModel, ProjectsViewModel (state holders)
ui/          ChatScreen, SettingsScreen, components
ui/effects/  SoundSynth, particle systems
renderer/    markdown + diff rendering
crash/       crash reporter
fcm/         push notifications
wearable/    Wear OS integration

The streaming is Server-Sent Events. The app opens a long-lived connection to /chat/stream, and the server pushes events as they happen: the agent's text tokens arriving, tool calls firing, results completing. You watch the agent work in real time. That alone was a revelation after Telegram's send-and-wait model.

Inline Edit Approvals

When the agent calls edit_file or apply_patch, the server holds the edit as pending and pushes it to the app as an approval card — a red/green diff with two buttons:

┌─────────────────────────────────┐
│ ✏️  src/server.js               │
│ ─ const old = thing;            │
│ + const old = thing || fallback;│
│                                 │
│        [ Apply ]  [ Reject ]    │
└─────────────────────────────────┘

The agent never applies an edit you haven't seen. There's an autonomous mode too, but the default is human-in-the-loop — because the default should be safe.

The Build Pipeline (Or: The Loop That Made It Real)

This is the part that made the whole project click, and I want to dwell on it.

A phone app is useless if you can't get it onto the phone. So I built a build and ship pipeline that runs entirely on my own network:

  • A publish.sh script builds the APK, names it with the build number + commit hash (robotnerd-69-f90384b.apk), and copies it to an archive directory.
  • A tiny APK server (a static file server) serves those builds.
  • The phone downloads them over Tailscale — no app store, no review process, no cloud dependency.

This is the loop that defines the whole project:

agent edits code → agent builds the APK → agent publishes it → I open the URL on my phone → install → test → repeat

A complete build-and-deploy cycle in minutes, all on hardware I own, over a network I control. The tool ships itself. This is what I mean by self-enabling — the app isn't just something I use, it's something that upgrades itself by writing its own software. I think of a feature, I describe it, and minutes later it's in my hand.

That loop is the real product. Everything else — the chat, the diffs, the sounds — exists to serve that loop.

Local-First, Modular Providers

The agent talks to any OpenAI-compatible endpoint. I can point it at:

  • A cloud API (Z.ai, DeepSeek, Cerebras) for heavy lifting
  • A local Ollama instance on another machine on my tailnet — fully offline, fully private, no per-token cost
  • Any combination — swap providers mid-session if I want a different model's strengths

This is the "software hot rod" principle: local-first by default, with the modular capability to switch to a service when you want one. Nothing is locked in. The intelligence is a swappable part. You keep everything on your own hardware as much as you can, and you reach for a cloud service on your own terms, not because the architecture forced you to.

The Moment It Worked

I remember the first time I opened the app on the couch, typed a request, and watched the agent's response stream in word by word. It felt like talking to something present — not sending a letter and waiting for a reply, which is what Telegram always felt like.

The app crashed plenty in those early days. That's just what happens when you build rich UI fast. But every time it did, I'd switch to the Telegram bot — still running, still solid — fix the problem, publish a new build, and try again. The stone knife built the laser. And the laser kept getting sharper.

By the end of this phase I had a streaming chat app with inline approvals, push notifications, a build pipeline over Tailscale, and multi-provider support — all running on my own network. The foundation was real.
