0x7: Day 1: A Telegram Bot That Codes

DATE: 2026-07-11 | PROJECT: ROBOTNERD

Every project has to start somewhere, and "somewhere" is almost never the elegant final architecture. RobotNerd started as a Telegram bot.

Not because Telegram was the right home for it — it absolutely wasn't — but because Telegram let me spend zero seconds on UI and all seconds on the brain. A bot is just a webhook: you send it text, it sends text back. No screens to design, no layouts to debug, no build pipeline. The fastest path to "can this thing actually code?" was to ask it through a chat I already had open.

The Agent Loop

The core is a standard pattern by now, but it's worth stating plainly because every later phase is built on it. The agent is a loop:

  1. Send the conversation (system prompt + history) to an OpenAI-compatible model with a set of tool definitions.
  2. The model either responds with text (done — show the user) or with one or more tool calls (it wants to do something).
  3. Execute each tool call — read_file, run_command, whatever — and append the results back into the history as tool messages.
  4. Loop. The model sees the results and decides what to do next.

That's it. The intelligence is the model; the agent is the harness that gives the model hands. The art is entirely in which hands and what happens when the hands fumble.

The Tools

The tool set is deliberately small and deliberately general. Here's all of them:

Tool Purpose
list_directory See what's in a folder
read_file Read a whole file
write_file Create or replace a file entirely
edit_file Modify a file (full content, diff for approval)
apply_patch Apply a unified diff — the token-efficient editor
run_command Execute shell — builds, tests, git, anything
change_project_directory Switch the working root
start_background_process Launch a long-running server/watcher
get_process_logs Read a background process's output
kill_process Stop one
list_processes See what's running

The first six are the editor. run_command is the escape hatch — it can build, test, lint, git commit, install deps, anything a developer would type. The last four manage long-running processes, which matters because "start the dev server and watch its logs" is a thing a coding agent genuinely needs to do.

apply_patch: The One That Matters

Here's a philosophical choice that paid off immediately. Most early "AI editor" implementations had the model output the entire new file for every edit. If you have a 400-line file and you want to change one line, you regenerate all 400 lines. That's slow, expensive, and — critically — fragile. The model will almost reproduce the file, and the one line it drifts on is a silent bug.

So there's apply_patch. The model outputs a standard unified diff:

--- a/src/server.js
+++ b/src/server.js
@@ -42,7 +42,8 @@
     return {
       id,
-      title: meta.title,
+      title: meta.title || `Session ${id}`,
+      fallback: !meta.title,
     };

Only the changed lines and their context are generated. It's cheaper, it's auditable (you can see exactly what moved), and — because it later got a fuzzy fallback matcher — it's resilient. If the model's context lines don't exactly match the file (whitespace drift, off-by-one line numbers), the patcher tries to locate the nearest matching region instead of failing hard.

This single tool probably saved more tokens and prevented more bugs than any other decision in the project.

The Two Problems That Eat Agents Alive

A tool-calling loop is powerful, and that's precisely the danger. Two failure modes will eat an autonomous agent alive if you don't build for them explicitly.

1. The Infinite Loop

The model gets stuck. It calls run_command to fix something, the fix doesn't work, so it calls run_command again — same command, same result, same conclusion, forever. Or it edits a file, the edit introduces a syntax error, it tries to fix the error, the fix introduces a different error, and it ping-pongs between two broken states until the context window overflows.

The naive guard is an iteration cap: "stop after N turns." But that's a bludgeon. The interesting fix is structural loop detection — actually inspecting the sequence of tool calls for repetition. If the same tool is operating on the same target (same file path, same command) more than a couple times in a window, that's not progress; that's a rut. Detect it, interrupt, and inject a system message: "You appear to be in a loop. Change your approach."

This turned out to be the difference between an agent that occasionally spins its wheels and one that genuinely self-corrects. The reflection prompt is surprisingly effective — given the nudge, the model will step back, re-read the situation, and try something actually different.

2. Self-Destruction

The scarier one. The agent can run any shell command. The agent is also editing the very server it's running on. Sooner or later, it edits a file, introduces a syntax error, the process crashes — and now the thing that could fix it is the thing that's dead.

This is the self-healing recovery system. It's a separate systemd service (OnFailure) that watches the agent process. When it dies, the recovery service:

  1. Runs git stash or git checkout to revert the working tree to the last known-good state.
  2. Restarts the agent.
  3. Leaves a recovery notice — a file the agent reads on startup that says "your last edit crashed this process; here's what was reverted."

So the agent wakes up, learns it nuked itself, and — because the notice is injected into its context — can investigate what went wrong without repeating it. It's an immune system. The agent can break itself, and it'll heal, and it'll know it healed, and it'll learn.

There is something quietly uncanny about watching that work.

Multi-Provider LLM Support

One practical detail that mattered more than expected: the agent talks to the OpenAI SDK, but the endpoint is configurable. Point it at the real OpenAI API, or at a local Ollama instance on the Tailscale network, or at any OpenAI-compatible provider (DeepSeek, Cerebras, GLM).

This meant I could experiment with different models for different jobs — a cheap fast model for the agent loop, a smarter one for the hard reasoning — and it meant the whole system could run offline on local hardware. The provider became a config knob, not an architecture decision.

It also, later, became the seed of the tailnet provider-discovery feature: detect Ollama instances on the network, list their models, switch providers from the app. But that's a later devlog.

What Telegram Gave Us

For two days, Telegram was the perfect incubator. I could test the agent from my phone while walking to the kitchen. I could see the tool calls happen in real time as messages. I could focus entirely on the questions that mattered:

  • Does the loop terminate?
  • Are the guardrails catching the failure modes?
  • Is apply_patch actually saving tokens?
  • Can the agent recover from breaking itself?

By the end of day two, the answer to all four was yes. The brain worked.

The problem was that the brain was trapped inside a 4096-character-message, no-streaming, no-diff-rendering, no-approval-buttons Telegram chat. It was time to build a body.
