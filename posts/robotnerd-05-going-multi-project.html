0x2: Going Multi-Project

DATE: 2026-07-19 | PROJECT: ROBOTNERD

For most of its life, RobotNerd had one project: itself. You opened the app, you talked to the agent, it worked in robot_nerd/. Sessions were a flat pile of files named session_<timestamp>.json — no titles, no summaries, no memory of which project they belonged to.

It worked. But the whole point was a coding companion for any project — the website, the CLI tool, the next idea. So the final phase was architectural: turn "a chat that happens to edit files" into a multi-project system where every project owns its history.

And then, building that system, I discovered something that perfectly illustrates why you keep your fallback around: there were two Telegram bots, and one of them had been quietly holding sessions the whole time. More on that at the end.

The Design: Projects as Directories

The new model, written up in a living PROJECT_PLAN.md mid-build, is built on a simple idea: every subdirectory of ~/Documents is a project. Zero config. robot_nerd (this app's own source) is just another project — self-referential, which makes it a perfect dogfooding target.

Each project owns a .robotnerd/ directory inside itself:

Documents/<project>/
  .robotnerd/
    project.json              # { displayName, activeSessionId, ... }
    summary.md                # AI-generated persistent context
    sessions/
      1783738488310.json          # message history
      1783738488310.meta.json     # { title, createdAt, updatedAt }

Projects are self-contained and portable — their entire state lives with them. Copy the directory, you copy the history.

Project Switching Is a Transport Concern, Not an Agent Concern

Switching projects is a dedicated HTTP endpoint that the app calls directly. It never touches the agent loop — the LLM cannot see, call, or handle it. The agent just wakes up in a different directory. Its tools operate relative to the project root. It has no concept of "project" — it sees a folder. Clean seam.

The UI: Projects in the Top Bar

A horizontal, scrollable project bar at the top. Below it, a session list for the active project: titled, dated cards. Tap one to open the chat. One chat at a time, with easy back-navigation. The session list is the tab equivalent.

┌─────────────────────────────────────┐
│ [robot_nerd] [website] [cli-tool] ⚙ │  ← scrollable project bar
├─────────────────────────────────────┤
│ ▸ Sessions                    + New │

The Migration (and the Bugs)

To move from the flat legacy pile to the new structure, I wrote a migration script. It introduced three bugs that I didn't catch until the app showed zero sessions:

  1. Floating-point timestamps. Node's stat.mtimeMs returns floats. Android's Long deserializer throws on fractions. One float killed the entire session list. Fix: Math.round() everywhere.
  2. Filename mismatch. History copied as session_<ts>.json, meta written as <ts>.meta.json. They never aligned. Fix: strip the prefix.
  3. Bogus timestamps. File-copy times, not real activity times. Fix: the session IDs were the real Date.now() timestamps — use those, and recover genuine mtimes from the originals where they survived.

Titles From Git

With timestamps fixed, all 36 sessions were still titled "Migrated session." So I derived real titles from the git history — each session's time-window mapped to the commits that landed during it. The session list became a readable timeline of the entire project, reconstructed from its own commit log.

The Two Bots (Or: Why You Keep Your Fallback)

Here's the discovery that ties this whole series together.

When I went to write these devlogs, I realized the migration had only captured some of the history. The reason? There were two copies of the Telegram bot, and the running service used the standalone one — not the copy inside robot_nerd that the migration had pulled from.

The running bot had been writing sessions to its own directory the entire time. Fifteen sessions — including the pivotal "let's build the non-telegram app" planning session, and the crash investigations — existed only in that standalone directory. They'd been invisible to the app the whole time.

This is the stone knife lesson, one more time. The fallback you keep running doesn't just save you when the new thing breaks — it accumulates its own history, its own value, parallel to the main path. I'd been using the bot throughout the entire build — to plan, to debug, to recover — and that work was real, it just lived in a different place. Migrating those 15 sessions in completed the picture: 53 sessions, fully chronological, telling the complete story of the build from both transports.

I migrated all 15, titled them from the git history the same way, and now the session list is whole. The app's history matches the reality of how the thing was built: two mouths, one brain, interleaved all along.

What This Enables

Open the app. See your projects in a bar across the top. Tap one. See every session that ever happened in it — titled, dated, real. Tap one and pick up where you left off. Or hit "+" and the agent's working directory and context automatically match the project you chose.

This is where the "software hot rod" vision starts to pay off across multiple projects. The agent that built RobotNerd can now work on the website, the CLI tool, whatever's next — each with its own history, its own context, its own sessions. Local-first, modular, self-enabling. The same loop — describe, build, ship, install — now applies to anything in your Documents folder.

The Record of Its Own Making

There's something I find deeply satisfying about how this ended.

The session list — 53 entries, titled, chronological — is the story these devlogs tell. Every phase, every bug, every synth oscillator, every crash reporter endpoint: it's all there, reconstructed from the commits. The app isn't just a tool. It's a record of its own making.

And it was built by talking to the thing it became. The first lesson of this whole project might be the simplest: build your tools to build your tools. Once you have a coding companion that can upgrade itself, everything after that is faster. That's the hello world of this era. Not print("hello") — build the thing that prints hello for you, then ask it what else it can do.
